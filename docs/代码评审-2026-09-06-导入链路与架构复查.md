## 2. 残留与新发现问题清单

编号 N 系列(N = New/Remaining),按优先级排序。P0 = 直接构成导入体验阻断或数据破坏风险;P1 = 主要流程数据不一致/明显性能损失;P2 = 次要缺陷或体验问题。

### P0:导入性能的两个硬伤

**N01 图片/视频双重全量哈希(双倍读盘)**

`pipeline.ts:87` 对每个文件先算一次 `sha256File(path)` 用于判重;随后 `extractContent` 内部 `extractImage`(extractor.ts:84)和 `extractVideo`(extractor.ts:121)又各自再算一次 `sha256File(path)` 生成缩略图文件名。同一个文件全文读盘两次。1GB 视频导入即 2GB 读盘;叠加 6 路并发,导入大文件夹时磁盘被打满、系统卡顿的直接来源。

修法:把哈希作为参数传下去——`extractContent(path, thumbs, hash)`;或提取结果带出哈希由调用方复用。改动小、收益立竿见影。

**N02 启动全量重扫 + 哈希前无 stat 预检**

两处叠加:

1. `watcher.ts:35` `ignoreInitial: false`——每次启动 chokidar 对所有监控目录重放全部 `add` 事件;
2. `pipeline.ts:87-89` 先 `sha256File`(全量读盘)再查 `pathRow` 判重——判重发生在哈希之后。

结果是:**每次启动都把监控库里所有文件完整读一遍盘、算一遍哈希,只为得到"已存在,跳过"**。懒启动会话(不弹窗)只是遮住了 UI,没有省掉任何 I/O。十 GB 级监控库 = 每次启动数十 GB 无效读盘。

修法(三层):
- `contents` 表加 `file_size` + `file_mtime` 列(已有 file_size,补 mtime 即可);
- indexFiles worker 开头先 `stat`:与库内 (path, size, mtime) 一致 → 直接跳过,不读文件内容;
- 哈希结果与 stat 一起写回,`change` 事件靠 mtime 变化触发再全量哈希。
- 可选:`ignoreInitial: false` 保留(作为"漏事件自愈"手段),有 stat 预检后它的代价就只剩目录遍历,可接受。

> 注:organizer 的 `scanAndHash`(duplicates.ts)是第三条独立哈希路径,`file_hashes` 表存了 `size` 却没有 mtime、也不做增量判断,每次扫描仍全量重哈希。修 N02 时应一并统一(见架构节)。

### P1:数据一致性与耐久性

**N03 本地推理无批处理,吞吐受限**

`local.ts` 的 `embedTexts`/`embedImages` 都是 for 循环逐条喂 ONNX(batch=1),`info.supportsBatch: true` 声明与实现不符。外层 `MAX_ACTIVE=6` 并发 + `RunMutex` 串行,6 个任务在互斥锁上排队——CPU 利用率取决于单条推理,大批量导入时向量化速度上不去。ONNX 导出模型本身支持 batch 维度(BERT/CLIP 均可),在 `mutex.run` 内合并 batch(如 ≤16)是一次投入、长期收益的优化。图片路径还需预处理(sharp 解码)与推理流水线化。

**N04 退出时丢向量,且内容不再补嵌(静默残缺)**

向量写入走内存缓冲(embedding-pipeline.ts:44-54,≥32 条或 5 秒 flush)。`index.ts` 的 `will-quit` 只做 `stopWatching()`(且未 await)+ `closeDb()`,**没有 flush 嵌入缓冲**。而 `pipeline.ts` 插入 contents 时 `needs_reindex` 默认 0。组合后果:导入进行中退出应用 → 缓冲中的向量丢失 → 这些内容 `needs_reindex=0`,**除手动触发补扫外永远不会被重新嵌入**,语义检索静默搜不到。R14 修的是"flush 成功才标记完成",但没覆盖"退出前必须 flush"这一环。

修法:`will-quit` 里同步 `flushAll()`(缓冲至多几十条,LanceDB 单次批量写很快),并给 embedding-pipeline 导出 flush 接口;closeDb 改为在 flush 完成后调用(event.preventDefault + 异步收尾后 quit,或至少接受"退出时尽力 flush")。

**N05 removeWatchDir / trashFiles 删除内容不清理派生数据**

`removeByPath`(pipeline.ts:151-161)是正确的:ftsDelete + 两张向量表 deleteVectors。但另外两条删除路径不完整:

- `ipc.ts` `files:removeWatchDir`(277-284 行):直接 `DELETE FROM contents`,**不清 FTS、不清 LanceDB 向量**;
- `executor.ts` `trashFiles`(136-143 行):同样只 DELETE contents。

后果链:① 孤儿向量留在 LanceDB,搜索 `limit=20` 的名额被死 ID 占据(hydrate 时丢弃,结果变少);② contents 与 contents_fts 行数不一致 → `db.ts:151-166` 的启动对账判定失配 → **下一次启动全量重建 FTS**(全库 bigram 重算,大库上明显拖慢启动);③ 每次整理丢一批文件就再触发一轮全量重建。

修法:这两处复用 `removeByPath` 的完整清理逻辑(抽成 `deleteContentCascade(id)` 统一调用)。另外 removeWatchDir 顺手把 `duplicate_groups` 全部 pending 清空(284 行)过于宽泛,建议只清受影响路径的组。

**N06 整理移动文件 = 资产身份重建**

`executeSuggestions` 的 move 分支只调 `safeMove` 动文件系统,不更新 `contents.source_path`。随后 watcher 触发旧路径 `unlink` → `removeByPath`(删记录+FTS+向量),新路径 `add` → 全新 contentId、重新哈希、重新提取、重新嵌入。后果:用户打的标签、关联笔记(notes.content_id)全部孤儿化;一次"整理"把该文件的全部索引工作重做一遍(还要吃 N01 的双倍哈希)。R05 只解决了"同路径内容变化",没解决"移动即换身份"。

修法(短期):safeMove 成功后,同 batch 内直接 `UPDATE contents SET source_path = to WHERE source_path = from`(参考已有的 `renameDir` 前缀替换 SQL),并同步 file_hashes;这样 watcher 的 add 事件会命中"同路径+同哈希→跳过",unlink 命不中旧路径成为 no-op。中期:按整改计划 6.2 的资产身份模型落地。

**N07 启动即三线并发,首分钟体验差**

`index.ts:69-96` 启动顺序:startWatching(全库重扫哈希,因 N02)→ reindexPending(可能一次性把数千条任务压进内存队列开始推理)→ RSS/Newsletter 调度器 → 最后才 createWindow。用户打开应用的最初几十秒,磁盘与 CPU 被后台任务占满,首屏渲染、首次搜索(还要冷加载 ONNX 模型)都慢。

修法:① N02 修复后重扫成本自然大降;② reindexPending 延迟到窗口 `ready-to-show` 之后 + 首个空闲回调(setImmediate 链或 requestIdleCallback 思路);③ 给嵌入队列加全局资源闸门(见架构节"任务编排")。

**N08 无单实例锁**

`index.ts` 没有 `app.requestSingleInstanceLock()`。双开两个实例 = 两个主进程并发写同一个 SQLite(WAL 能扛)和同一个 LanceDB 目录(lancedb.ts 自己的注释明确说并发写会清单失配损坏)。用户双击图标两次就可能造成向量库损坏,然后触发 R16 重建、历史向量丢失。一行锁 + `second-instance` 里聚焦已有窗口,必须加。

**N09 IPC 暴露任意路径读写**

`io.ts:159-165` 的 `readTextFile`/`writeTextFile` 对路径零限制,经 `io:readFile`/`io:writeFile` 直接暴露给渲染进程;`oasis-media://raw?p=<绝对路径>`(index.ts:33-37)可读任意图片。渲染端有 CSP(script-src 'self')兜底,且未发现 dangerouslySetInnerHTML,当前直接可利用性低;但这个应用渲染远程内容(RSS/平台收藏/Newsletter),一旦任何第三方 HTML 进入渲染层形成脚本执行,就是全盘任意文件读写。纵深防御应收口:io 读写限定在用户显式 pick 的路径或应用数据目录;raw 协议限定在已入库的 source_path 白名单。

### P2:次要缺陷

**N10 整理 tag 动作覆盖已有标签**(executor.ts:52):`UPDATE contents SET tags = ?` 直接覆盖,不合并;且标签值借用 `target_path` 字段传递,语义混乱。

**N11 importJson 不进 FTS 也不进嵌入队列**(io.ts:126-129):JSON 导入的收藏只有 SQL LIKE 可搜(还要等下一次启动 FTS 对账重建才进 FTS),语义检索永远搜不到。与 R19(平台收藏入队)不一致。

**N12 `embedderStatus()` 硬编码全部 ready**(search.ts:206-213):与 `embedderReadiness()` 矛盾,设置页/诊断页据此展示会误导用户。

**N13 chunkText 可产生空片**(embedding-pipeline.ts:346-347):`buf` 为空且 `rest.length === maxLen` 时 `chunks.push('')`,空字符串进嵌入调用。加 `if (buf)` 守卫即可。

**N14 模型不就绪的行永久滞留 needs_reindex**(embedding-pipeline.ts:151-158):图片模型缺失时这些行每次 reindexPending 都被整页取出又放回,永不退出扫描集。建议给个 `last_attempt_at` 节流。

**N15 will-quit 不等待异步收尾**(index.ts:102-105):`void stopWatching()` 后立刻 `closeDb()`,watcher 关闭与在途 indexFiles 写库可能撞上"database closed"异常退出。配合 N04 一并改为异步收尾后 quit。

**N16 死依赖与无增量扫描**:p-queue 在依赖里但全项目未使用(嵌入队列是手写闸门);scanAndHash 无 mtime 增量(并入 N02 统一治理)。

**N17 OCR 级联任务使计数漂移**:runJob 内 OCR 成功后 `enqueueTextEmbed` 追加任务,但 embedTotal 已在 endIndexSession 固定,多出的 tick 使 embedDone 提前"达标",完成报告数字轻微失真(cosmetic,收敛机制能兜住)。

**N18 `files:getStatus` 的 isScanning 硬编码 false**(ipc.ts:191):UI 无法展示真实扫描态,可从 import-progress 的 phase 推导。

**N19 window.open 未设 setWindowOpenHandler**(DetailModal.tsx:69):外链应走 `shell.openExternal` 并在主进程拦截 `_blank`,防止未来某次改动让远程页面在 Electron 窗口内打开。

## 3. 架构评估

### 3.1 现状结构(事实描述)

业务全部集中在主进程的模块化单体:渲染层 React+Zustand → preload(类型化 API 面,约 60 个通道)→ 主进程按域分模块(indexer/embedder/organizer/platforms/subscriptions/video/io)。存储三件套:SQLite(结构化+FTS5)、LanceDB(向量,带写锁与损坏自愈)、文件系统(缩略图/HEIC 缓存/模型)。这个骨架对单机桌面应用是合理的,问题不在分层,在以下四个结构性缺口:

### 3.2 结构性问题

**A. 哈希能力三分天下,没有统一的"文件指纹缓存"。**
pipeline(indexFiles)、extractor(缩略图命名)、organizer(scanAndHash)各自调 `sha256File`,互不复用;`contents` 存一份 hash、`file_hashes` 又存一份 sha256+phash。同一个文件在被整理过的库里的"完整读盘次数"是 3 次/首轮 + 3 次/每次重启。这是导入慢的结构性根源。
→ **建议**:抽一个 `fingerprint.ts`:`getFileFingerprint(path)` 内部做 stat 预检 → 命中 (path,size,mtime) 缓存直接返回 → 未命中才算哈希并回写(缓存表建议直接用 contents + file_hashes 统一后的形态)。所有调用方收敛到这一处。

**B. 嵌入任务是纯内存队列,无持久化、无生命周期协议。**
`waiting: Job[]` 在内存里,退出即蒸发(N04);`needs_reindex` 是唯一的"待办"持久化,但它语义混杂(既是"待嵌入"又是"失败重试"又被用作"跳过标记" N14);进度会话、队列、SQLite 标记、LanceDB 写入四者之间没有统一的提交语义(整改计划 3.3-3 已经指出,目前只做到 R14 的单点诚实化)。
→ **建议**(务实版,不必上完整任务表):① 退出 flush(N04);② 插入 contents 时先置 `needs_reindex=1`,向量持久化成功才清零——这样任何时点退出,下次启动 reindexPending 都能自愈,一行改动消灭整类丢任务问题;③ 给 needs_reindex 行加 `last_attempt_at`,失败退避。

**C. 派生数据生命周期没有唯一责任方。**
"一条内容"的派生数据分布在 contents 行、contents_fts 行、两张 LanceDB 表、缩略图文件、file_hashes 行。现在有三种删除实现(removeByPath 完整、removeWatchDir/trashFiles 残缺、renameDir 只改 path),每次新增删除/移动入口都要人工记得清五处。
→ **建议**:收敛为唯一的 `contentRepository.delete(id)` / `.movePath(from,to)`,所有入口调用;这也是 N05/N06 的根治。

**D. IPC 面大而无校验,主进程对渲染进程全信任。**
约 60 个 handle,参数直接进 SQL/文件系统/子进程;无 schema 校验、无路径边界检查(N09)、重命令(platform:retag 逐条 await)阻塞 IPC。CSP 是当前唯一的防线。
→ **建议**:① 敏感通道(文件读写、reveal、reveal 相关)加路径白名单校验;② 参数用 zod 之类在注册层统一校验(可渐进);③ 长任务(retag/scan)改为任务+进度事件模式,与导入进度同一套机制。

### 3.3 启动与并发编排

现状是"启动即全速":重扫(N02)+ 补嵌入 + 调度器同时起跑,与 UI 抢资源;索引 6 并发、嵌入 6 并发、organizer 1 并发,各自为政,没有全局 I/O/CPU 预算。建议引入一个极简的"资源闸门"(甚至不需要 p-queue,一个带优先级的信号量即可):用户可见操作(手动加目录、搜索)高优先级,启动重扫/补扫低优先级,空闲时段跑。

### 3.4 值得保留的设计

批评之余,这些是做得对的,后续改动不要破坏:LanceDB 写锁+维度守卫+损坏自愈(R12);向量批量写缓冲;import-progress 的双通道收敛(事件+轮询)与诚实化失败统计(R17);路径边界精确匹配(isUnderRoot);safeMove 的防覆盖/防自删(R03);FTS bigram 中文方案与对账自愈;懒加载重依赖(pdf-parse/mammoth 动态 import)。

## 4. 修复路线建议

按"投入/收益/风险"排的务实顺序,不对应原计划的阶段字母:

**第一批(1–2 天,全是小改动,导入体感质变)**
1. N01 哈希传参复用(extractor 签名加 hash 参数)。
2. N02 stat 预检:contents 加 file_mtime 列(迁移安全,ALTER TABLE ADD COLUMN),indexFiles 先查 (path,size,mtime) 命中即跳过。
3. N04+N15 退出收尾:will-quit 同步 flushAll + 修 needs_reindex 初值(见 3.2-B②)。
4. N08 单实例锁(3 行)。
5. N05 抽 deleteContentCascade,三处删除统一。

**第二批(2–3 天,一致性与体验)**
6. N06 移动保身份(UPDATE source_path 方案)。
7. N07 启动编排:补扫延后 + 资源闸门。
8. N12/N18/N13/N10 小修。

**第三批(按需规划)**
9. N03 真 batch 推理 + 图片预处理流水线。
10. N09/N19 安全收口。
11. 哈希缓存统一(file_hashes 并轨)、N11、N14、N16。

**验证方式**(每批做完跑一遍):
- `npm test` 保持绿;新增回归:chunkText 空片、stat 预检命中/未命中、退出 flush 后重启无 needs_reindex=0 的无向量内容(`diag:indexStats` 里 pending 应与 LanceDB 行数对得上);
- 手工场景:① 重复启动三次,用 `fs_usage`/活动监视器确认监控库无全量读盘;② 导入含 1GB 视频的文件夹,确认读盘量 ≈ 1×文件大小;③ 导入中途 Cmd+Q,重启后语义检索能命中刚导入的文件;④ 移动一个已打标签的文件,标签与向量保留。

## 5. 一句话总结

上轮修好了"卡死",这轮剩下的是"慢"与"脆":**每个文件多读一遍盘(N01)、每次启动全库重读(N02)、退出丢向量(N04)、三条删除路径清理不一致(N05)、移动即身份重建(N06)**——五个问题环环相扣,共同构成"导入文件的时候问题很多"的体感。第一批五个小改动落地后,导入链路的性能与可靠性会上一个台阶;架构层面的长期功课是文件指纹缓存、任务持久化和派生数据唯一责任方这三件事。
